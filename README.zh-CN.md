# kill-code：用软件工程的方法驯服 AI 编码

[English](./README.md) | [中文](./README.zh-CN.md)

## 一、当前 vibe coding 的困境与根因

### 1.1 一种"跟着感觉走"的编程方式

Vibe coding 在 2025 年成为柯林斯词典年度词汇，其核心姿态是：开发者用自然语言描述意图，把"怎么实现"几乎完全交给 LLM，凭"感觉"接受或拒绝生成结果。承载这种姿态的，是 Claude Code、Codex、Cursor 这一类基于 **ReAct（Reasoning + Acting）** 思想的自主编码智能体。

### 1.2 表象问题

随着大规模落地，问题集中爆发：

- **业务逻辑盲区**：LLM 能生成语法正确却语义错误的代码——订单查询缺权限校验、支付金额直接信任前端、审批流程可被绕过。传统安全工具几乎看不见这类漏洞。
- **幻觉与供应链污染**：LLM 会"自信地"推荐并不存在的依赖包，攻击者据此抢注投毒。
- **可维护性塌陷**：生成代码缺乏一致架构，技术债快速累积；出了 bug 陷入"vibe debugging"——人和 AI 都说不清为什么坏。
- **责任真空**：当代码造成实际损害，责任归属（提示者 / AI 提供方 / 部署方）没有共识。

### 1.3 根因：全量上下文灌入 + ReAct 线性累积

主流编码智能体的工作循环是：

```
Context_t = Context_{t-1} + Thought_t + Action_t + Observation_t
```

每一步推理，都把**所有历史思考、动作、观测**重新灌入 LLM。这带来三个结构性后果：

1. **上下文窗口爆炸**：token 快速消耗，很快触及模型上限。
2. **目标漂移**：通常 7–8 步之后，原始目标在巨大上下文里被稀释，LLM "忘了自己要干什么"。
3. **信噪比恶化**：上下文越大，无关信息越多，幻觉概率越高，生成越不稳定。

**本质问题**：vibe coding 把"一个复杂系统所需的全部知识"一次性、全量地灌给 LLM，让它在巨大上下文里自己摸爬滚打。这恰恰违背了人类软件工程师处理复杂性的基本方法。

## 二、传统软件工程是怎么做的

### 2.1 信息隐藏：模块化的第一性原理

1972 年，David Parnas 在《On the Criteria To Be Used in Decomposing Systems into Modules》中明确提出：**不应按流程图分解系统**，而应按"可能变化的设计决策"来划分模块。每个模块隐藏一个"设计秘密"，只通过稳定接口暴露必要能力。他给出三个评估维度：管理收益、产品灵活性、可理解性。

### 2.2 单一职责原则

Robert C. Martin 把 Parnas 的信息隐藏、Dijkstra 的关注点分离、Constantine 的内聚/耦合思想整合为 SOLID 中的 **S——单一职责原则**：

> 一个类/模块应该有且仅有一个引起变化的原因。

职责扩散是坏味道的源头：一个模块同时承担 P1、P2，改 P1 就可能破坏 P2。

### 2.3 设计模式：把"变化"封进可控边界

- **策略模式**：一簇算法各自封装，消除 if-else 分支，新增策略不改老代码（开闭原则 + 单一职责）。
- **责任链模式**：多个处理者串成链，每个节点只做一件事，请求沿链传递。
- **模板方法模式**：算法骨架不变，可变步骤延迟到子类。

它们的共同目标是**高内聚、低耦合**——每个单元职责单一，持有的知识最小。

### 2.4 传统做法的关键特征

> **先定边界，再写代码；给每个模块"刚好够用"的信息，而不是全量知识。**

设计模式本质上是**上下文隔离机制**：把不必要的知识挡在模块边界之外。一个负责"金额格式化"的函数，不需要知道整个订单系统的业务规则。

## 三、核心观点：AI 编码也必须回到软件工程

### 3.1 两种思路的对比

| 维度 | vibe coding / ReAct 智能体 | 软件工程方法 |
|------|---------------------------|--------------|
| 上下文策略 | 全量灌入，越大越好 | 最小够用，按模块裁剪 |
| 模块边界 | 模糊，由 LLM 自行决定 | 先固化，逐层确认 |
| 知识传递 | 所有知识都给 LLM | 只给当前单元需要的 |
| 复杂度应对 | 靠堆上下文窗口 | 靠拆分 + 设计模式 |

### 3.2 核心主张

让大模型写一个简单函数，准确率非常高；让它写一个复杂系统，问题百出。差距不在模型能力，而在**任务规模**和**上下文纯度**。

因此本方案的路径，是**把软件工程的每一步都严格执行**——只是每一步都由"AI 起草初稿 + 人工确认"完成，设计模式作为拆分脚手架贯穿其中：

1. **AI 编写设计方案初稿**：确定模块边界与职责 → 人工确认。
2. **AI 选择设计模式组合**（责任链 + 策略 + 模板方法等）初稿 → 人工确认。
3. **在设计模式的干预下，AI 把复杂问题层层拆解**——拆成多个策略，每个策略再拆成多个函数 → 每一步人工确认。
4. **拆解到函数粒度后，AI 为每个函数构建最小够用的特有上下文，完成编码。**

**本质**：人不再写代码，也不替 AI 做设计；但人在每一个软件工程的关键节点把关。设计模式的作用是让"拆分"有章可循，确保每个函数边界清晰、职责单一，从而让最后一步编码落在 LLM 的强项区间。

### 3.3 关键差异：最小上下文，而非最大上下文

这是本方案与 vibe coding 最根本的分野：

- **vibe coding**：不拆分，把所有背景知识全部灌给 LLM，依赖它在巨大上下文里自己理出头绪。
- **本方案**：经过前面层层拆分，每个函数的职责已经是单一的，它需要的知识本就是少量的——为其构建**特有的、最小够用的上下文**即可。

为什么要"最小"？

- 上下文越大，信噪比越低，幻觉越多；
- 职责单一的小函数，其所需知识天然是少量的；
- 给一个只做"金额格式化"的函数灌入整个订单系统的业务文档，那是噪声，不是信息。

**设计模式在这里的双重作用**：它不仅是人类可读的代码组织方式，更是**上下文裁剪的脚手架**——责任链的每个节点、策略的每个分支、模板方法的每个步骤，天然划定了"这个单元只需要知道什么"。

## 四、方案优势

1. **准确率跃升**：把复杂任务降到"函数级"，让 LLM 在它的强项区间工作。
2. **可维护性**：模块边界清晰，符合 SOLID，技术债可控。
3. **可追溯**：设计决策每个节点都有人工确认，可审计、可回放。
4. **可验证**：小函数易于单测，回归保护强。
5. **上下文经济**：token 不再爆炸，成本和延迟双降。
6. **责任清晰**：人负责把关确认，AI 负责起草和编码，分工明确。
7. **规避 vibe coding 核心风险**：从源头抑制业务逻辑漏洞、上下文漂移、目标遗忘。

## 五、结语

vibe coding 的问题，不是 AI 不行，而是把"处理复杂系统"这件事整体丢给 LLM + 巨大上下文。软件工程几十年沉淀的模块化、信息隐藏、设计模式，本质上就是在解决"如何驯服复杂性"。把它们重新引入 AI 编码，不是倒退，而是让 AI 在它真正擅长的尺度上工作。

## 六、为什么写下这篇文档

需要先说清楚：本文不是在宣扬一个观点，也不是对 vibe coding 做纯粹批判。写下它的目的，是为**构建一个遵循软件工程方法论的编码智能体**做准备——一个真正能解决 vibe coding 实际问题的智能体。

kill-code 想做的事情很朴素：把软件工程的每一步（设计、选模式、拆分、编码）固化成 AI 可执行、人可确认的流程，用设计模式把复杂系统一路拆到函数粒度，让 LLM 只在它擅长的尺度上工作，每个函数配以最小够用的特有上下文。

这件事一个人做不完。如果你也认为 AI 编码不该止步于"全量上下文 + 跟着感觉走"，如果你在 vibe coding 里被上下文漂移、业务逻辑漏洞、不可维护的代码困扰过——欢迎参与，一起把它做成可用的东西。
